# A/B 方案对比

## 结论

A 和 B 解决的是同一个可见副作用，但采用的范围不同：

- A 只还原有限的“自称句式”，目标是尽量保留正文中真实出现的产品名。
- B 与现有入站替换保持同一字面替换形状，反向还原配置 target，目标是完整覆盖生成文本中的 target。

A 可运行，但存在已知的流式一致性瑕疵，因此只作为独立参考实现，不进入生产 patch。B 是本次 PR 的生产候选，代价是无法区分由身份替换产生的 target 和模型原本就在引用的真实产品名。

## 核心区别

| 项目 | A：自称句式 | B：全文反向替换 |
|---|---|---|
| 处理范围 | 只处理已知自称结构中的 target | 处理响应可见文本中的精确 target |
| 产品名保留 | 普通正文中的产品名不改写 | 已知产品名也可能被连带改写 |
| 身份来源 | 参考快照自行解析 `You are X` 等声明 | 从现有 `identity.replacements` 和原始请求推导 |
| 流式状态 | pending、上下文和改写长度需要协同 | 只保留 target 后缀和边界所需的有限上下文 |
| 覆盖能力 | 受模型措辞影响，开放式自称无法穷举 | 与入站字面替换对称，覆盖生成文本中的 target |
| 已知缺陷 | 参考快照存在 `10 / 3000` 流式一致性失败 | 无法恢复入站替换前已经丢失的产品名歧义 |
| 当前状态 | 可运行，标记为实验性参考实现 | 生产候选，已通过测试和独立复审 |

## A 方案

A 的设计价值是缩小改写范围：只有当 target 出现在“我是谁”一类结构中时才还原，普通正文提到的产品名保持不变。

参考实现包含三层：

1. 从原始请求的 `instructions`、`system` 或 `developer` 文本推断客户端身份。
2. 用有限句式识别 target 是否处于自称位置。
3. 在流式路径中暂存可能被分片截断的句式，并在流结束时处理尾部。

主要限制：

- 模型可使用固定词表之外的措辞，无法保证所有自称都能识别。
- 跨流式分片时，需要同时维护待判定文本、最近上下文和已还原长度。
- 重复或重叠身份片段会暴露状态机的不一致性。
- 当前参考快照仍使用自己的 `You are X` 解析器，没有把现有替换配置作为客户端身份的唯一事实来源。

实测以 A 自身的整段改写结果作为期望值，使用 seed `7`、3000 组文本和随机 1 到 4 字节切片：

```text
failures = 10 / 3000
ratio    = 0.33%
```

因此 A 的状态是“可运行、可审查、有已知瑕疵、已搁置”，不是生产合并候选。参考包内保留源码、测试、patch、设计说明和可复现失败的诊断测试。

## B 方案

B 复用现有入站替换规则，把响应文本中的 target 反向替换为当前请求推断出的客户端身份。实现只修改响应正文和 reasoning 文本，不修改上游请求，也不建立跨请求状态。

实测结果：

```text
流式/聚合确定性等价测试 = 0 / 3000 失败
```

性能测试使用 20KB、target 密度很高的合成文本：

```text
单次处理       约 0.30ms
64 字节分片    约 0.57ms
内存分配       4 allocs/op
```

这些数据只统计响应处理，不包含模型和网络耗时。

B 的已知取舍来自入站替换本身：身份名和真实产品名在进入上游前可能已经变成同一个 target，响应侧无法区分二者。因此 B 选择完整还原 target，接受真实产品名也可能被改写的风险。这是现有设计的信息损失，不是响应侧能够通过增加匹配规则可靠补回的信息。

## 不直接比较失败率

A 的 `10 / 3000` 是“A 自身整段语义下的流式一致性失败”，B 的 `0 / 3000` 是“B 全文反向替换语义下的等价性失败”。两者测试的是不同输出契约，不能把两个百分比当作同一功能的相对质量排名。

A/B 的共同价值是明确产品取舍：

- 要保留真实产品名，需要接受自称识别不完备，并继续解决流式状态问题。
- 要完整还原 target，需要接受产品名连带改写。

本 PR 选择 B，因为它的行为与现有入站替换对称、可确定验证，并且不会把身份识别建立在开放式句式猜测上。
